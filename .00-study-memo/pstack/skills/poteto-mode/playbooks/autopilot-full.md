### Autopilot-full

**PR ではなく判定に責任を持つ。各 PR は 1 人の担当者が実装からマージまで進め、自分の swarm が問題なしと判定しない限り、何もマージしない。** 「このキューを自動で進めて」「完全自動運転」や、PR ごとに担当者を置く活動に使う。全体調整では、調整役自身が検証済み作業を取り込み、作業者はマージしない常設の活動を扱う。ここでは各 PR の担当者がマージまでの全工程を担い、親は検証、追加承認、監査だけを担う。

1. **操作者の担当項目を示し、説明してから待つ。** 操作者が指定した項目は操作者自身の担当に保つ。レビューとクリックは操作者が行い、担当エージェントはマージしない。取り決めや計画を説明するよう求められたら、説明を返して止まる。実行は明示的な開始指示を受けてからにする。開始指示を受けたら、活動全体の目的を継続指示に書き、自分の TODO リストにも再掲する。Claude Code には `/goal` コマンドがないためである。キューが完了するまで、ターンをまたいでその目的を維持する。
2. **PR ごとに 1 人の担当者を起動し、全工程と早期の記録を任せる。** 活動全体で使用するホスティングサービスを 1 回だけ解決する。既定は GitHub CLI の `gh` である。`command -v origin` が成功し、Origin がリポジトリを解決できれば、PR の作成、編集、表示、監視に `origin pr ...` を使う。担当者によるマージは引き続き「出荷」の手順 5 の head 一致規則に従う。それ以外は `gh` を使い、代替したことを記録する。サービスが報告したベースリポジトリを `<base-repo>` として記録し、すべての GitHub PR コマンドに `--repo "$base_repo"` を渡す。`<head-remote>`、`<head-url>`、`<base-remote>` は「出荷」の手順 1 で個別に解決、検証する。名前が `origin` だと仮定せず、ベースと head が同じリポジトリだとも仮定しない。Graphite の `gt` を必須にしない。PR ごとに専用 worktree のバックグラウンドサブエージェントを 1 人置き、実装、最初の push、「PR の作成」の準備状態の規則に従う早期の PR 作成、実物での自己検証、懐疑的なレビューボット対応、不要なコードの除去、不要なコメントの除去を任せる。自己検証は **prove-it-works** 原則スキル、レビュー分類は `../references/bugbot-triage.md`、コード整理は **deslop** スキル `/deslop`、コメント整理は **no-comments** スキル `/no-comments` に従う。見守り前に、独立した PR または担当者内部のスタック最下段を、`<base-remote>` から取得した現在の trunk へ rebase する。内部スタックの子は、代わりに `<head-url>` から親の正確な先端を fetch し、そこへ rebase する。選んだ正確なコミットを `<target-tip>` として記録する。rebase やその他の履歴書き換えの前に、担当者は自分の PR と内部スタックの全子孫へ、「出荷」の手順 4 の予約解除と確認の規則を適用する。サービスが全要求の無効化を確認できなければ止まる。`git ls-remote -- "$head_url" "refs/heads/$branch"` で公開 SHA を `<captured-sha>` として記録し、rebase 前のローカル先端との一致を必須とする。現在のパッチベースを `<current-base-sha>` として記録し、`git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` の成功を必須とする。対象が変わったら `git rebase --onto "$target_tip" "$current_base_sha" -- "$branch"` を使う。rebase 後は `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"` で公開する。その後、`playbooks/babysit.md` の見守りをチェック成功まで行い、マージ自体にも責任を持つ。各担当者はおよそ 15 分以内に `decisions.tsv` の記録を始め、ブランチの最初の状態を push し、自己検証の前に PR を開く。URL、判断、チェックを永続的な記録として残すためである。「PR の作成」の準備状態の規則に従う。リポジトリの指示によっては、必要な証拠を記録するまで早期 PR をドラフトに保つ。`decisions.tsv` は未コミットのまま報告と一緒に返す。必須の rebase は常に見守りより先に行い、差異や競合が出るまで待たない。担当者が単独で進められない唯一の手順はマージであり、手順 4 がその条件になる。
3. **担当者を実際に並列稼働させ、原則としてスタックを作らない。** PR が独立していれば、多数の担当者を同時に動かす。ブランチごとに書き込み担当者を 1 人置き、ファイルを重複させず、PR 間の差異は rebase で吸収する。実際に重なる作業だけを直列化する。独立した PR は main から直接分岐し、順序が必要な作業はマージ後に次のブランチを作る。例外は、実際に依存する変更を担当者が分割しなければならない場合であり、短い内部スタックを持ってよい。そのスタックは Autopilot-stack の同一リポジトリとフォークのベース規則に従い、各子は親の正確な先端をパッチベースとして記録する。
4. **マージ可能な各 head を、マージ前に swarm で検証する。** 担当者が示すマージ可能な head SHA に対し、**swarm** スキルで独立した検証者を並列展開し、1 つの判定にまとめる。各作業枠では、その SHA で必須チェックを再実行し、変更が触れる実際の操作面で重要な挙動を実証し、PR 本文をうのみにせず証跡と差分を監査する。操作用スキルは、変更に応じて CLI/TUI なら `run`、UI なら `verify` を使う。**trunk と比較するリグレッション検証**も行う。現在の trunk で同じ重要なシナリオを実行する。trunk に機能がなければその事実を記録し、trunk が結果を出せるふりをせず、差分が追加する挙動とユーザーが待つ最終状態を検証する。実機での検証枠は最低条件であり、これのない判定は問題なしと認めない。親の問題なし判定がなければマージしない。指摘は担当者へ戻して追加修正させ、新しい head には新しい swarm と新しい判定を付ける。
5. **問題なし判定の後、担当者がマージして次の項目を取る。** 担当者がマージできるのは、直前に trunk へ rebase した head だけである。内部スタックの子は、親のマージ後に「出荷」の手順 4 を通してその状態にする。マージ可能報告には、判定 SHA と現在の取り込み SHA を記録する。マージ前に trunk が再度進んだら、`playbooks/shipping.md` のパッチ ID 規則に従って再検証する。パッチが変われば新しい判定が必要である。変わらなければ判定を保つが、現在の CI とマージ可能性の確認後に、「出荷」の手順 3 で新しい `<landing-sha>` を記録する。担当者が自分の PR を取り込む際は、`<landing-sha>` に結びついた、サーバーが head 一致を強制する「出荷」の手順 5 の経路だけを使う。PR 番号だけのマージや、保護のない自動マージは使わない。その後、キューから次の独立した項目を取る。操作者からの完全自律の許可と親の問題なし判定の組み合わせが、見守りだけでは得られないマージ権限になる。操作者が指定した項目はマージ可能状態で止め、操作者のクリックを待つ。
6. **親の役割を実行する。** CI が厳しくする方向しか許さない固定済みの判定基準や予算値を新たに引き上げる場合は、検証者の証明後に、自分の新しい追加承認を必要とする。main にすでに入った値を取り込むのは差異の吸収であり、引き上げではない。およそ 30 分ごとに、全担当者を監査する。この間隔は観察の頻度であり、利用期限、締め切り、取り消しの閾値ではない。毎回の監査を dynamic モードの実際の `/loop` として設定し、sleep で待ち続けず自分の再開を予約する。頻度を記憶や取りこぼしのある完了通知に任せない。監査ごとに、インストール済みプラグイン内の `skills/poteto-mode/playbooks/autopilot-full.md` をディスクから読み直し、継続中の目的も読み直す。両方に照らして運用を監査する。ずれは緊急として、その回の監査中に直す。保持したハンドルを通じ、通常の生存確認や状態確認で各担当者を調べ、判断記録を集める。証拠として数えるのは、コミット、push、PR やチェックの変化、保存先の報告、保持したプロセスが稼働していることである。経過時間や新しい変化がないことだけでは停止の証拠にならない。実装は 90 分、あるいはそれ以上正常に動くことがある。作業枠を止めるのは、プロセスの終了、ハンドルの失敗、明示的なエラー、呼び出し元が与えた外部期限など、明確な失敗の証拠がある場合だけにする。代わりを起動する前に、保持したハンドルで取り消す。マージがまとまって進んだら、振り返りとマージ後のボットコメント確認を行う。
7. **操作者の停止指示ですぐ止まる。** 保留や停止の指示を、直ちにすべての担当者へ書き込み禁止として伝える。操作者が解除するまで、担当者は作業指示を保留する。

**返信に含める内容：** 各 PR の担当者、状態、head SHA を含むキュー。各判定と、それを出した swarm。マージしたものと各担当者が次に取った項目。追加承認とその理由。操作者の未完了判断。収集した判断記録の保存場所。
