### Autopilot-stack

**取り込みではなくスタックに責任を持つ。完全な自律性の下でキューを実装、検証し、操作者自身がレビューして取り込める 1 本のスタックとして渡す。** **Autopilot-full** と対になる手順書である。

1. **担当者の反復手順はそのまま使う。** 活動全体で使用するホスティングサービスを 1 回だけ解決する。既定は GitHub CLI の `gh` である。`command -v origin` が成功し、Origin がリポジトリを解決できれば、PR の作成、編集、表示、監視に `origin pr ...` を使う。この手順書ではマージしない。それ以外は `gh` を使い、代替したことを記録する。サービスが報告したベースリポジトリを `<base-repo>` として記録し、すべての `gh pr` コマンドに `--repo "$base_repo"` を渡す。`<head-remote>`、`<head-url>`、`<base-remote>` は「出荷」の手順 1 で個別に解決、検証する。名前が `origin` だと仮定せず、ベースと head が同じリポジトリだとも仮定しない。head リポジトリがフォークなら、その実体を検証し、所有者とリポジトリ名を `<fork-owner>` と `<head-name>` として記録する。Graphite の `gt` を必須にしない。PR ごとに専用 worktree のバックグラウンドサブエージェントを 1 人置き、変更の最初から最後まで任せる。実装、最初の push、「PR の作成」の準備状態の規則に従う早期の PR 作成、必須チェック・CI・証跡による自己検証、`../references/bugbot-triage.md` に従う懐疑的なレビューボット対応、**deslop** スキル `/deslop` によるコード整理、**no-comments** スキル `/no-comments`、`playbooks/babysit.md` に従うチェック成功までの見守りを担当する。作業が独立していれば担当者を並列稼働させる。各担当者はおよそ 15 分以内に、**show-me-your-work** スキルに従って `decisions.tsv` の記録を始め、ブランチの最初の状態を push し、自己検証前に PR を開く。リポジトリの指示によっては、必要な証拠を記録するまで早期 PR をドラフトに保つ。記録は未コミットにし、報告と一緒に返す。
2. **定期的な再開で監査する。** 親はおよそ 30 分ごとに監査する。この間隔は観察の頻度であり、利用期限、締め切り、取り消しの閾値ではない。毎回の監査を dynamic モードの実際の `/loop` として設定し、sleep で待ち続けず自分の再開を予約する。頻度を記憶や取りこぼしのある完了通知に任せない。監査ごとに、インストール済みプラグインの `skills/poteto-mode/playbooks/autopilot-stack.md` をディスクから読み直し、継続中の目的も読み直す。両方に照らして運用を監査する。ずれは緊急として、その回の監査中に直す。保持したハンドルを通じ、通常の生存確認や状態確認で各担当者を調べる。証拠として数えるのは、コミット、push、PR やチェックの変化、保存先の報告、保持したプロセスの稼働である。経過時間や新しい変化がないことだけでは停止の証拠にならない。実装は 90 分、あるいはそれ以上正常に動くことがある。作業枠を止めるのは、プロセスの終了、ハンドルの失敗、明示的なエラー、呼び出し元が与えた外部期限など、明確な失敗の証拠がある場合だけにする。代わりを起動する前に、保持したハンドルで取り消す。
3. **操作者の判断条件を守る。** 説明してから待つ。計画の説明を求める依頼は開始指示ではない。明示的な開始指示を受けたら、活動全体の目的を継続指示へ書き、自分の TODO リストにも再掲する。Claude Code に `/goal` コマンドがないためである。連鎖が完了するまで、ターンをまたいでその目的を維持する。操作者が停止を指示したら、すべての担当者を直ちに書き込み禁止で保留する。
4. **STACK-READY で検証する。** 担当者は正確な head SHA を添えて STACK-READY と報告する。親は **swarm** スキルに従ってその SHA を検証する。独立した検証者を並列展開し、その SHA で必須チェックを再実行し、最低条件として重要な挙動を実機で確認し、PR 本文をうのみにせず証跡と差分を監査する。swarm は結果を 1 つの判定にまとめる。指摘は担当者へ戻し、未検証のものをスタックに入れない。
5. **問題なし判定で末尾へ追加し、出荷しない。** 担当者はマージ、自動マージ予約、クローズを行わない。問題なし判定を得た PR を、検証した順序または操作者が指定した順序で、下から上へ固定した 1 つの一覧に追加する。同一リポジトリの head では、サービス上のベースブランチの連鎖もその順序を記録する。フォークの head ではすべての PR が trunk を対象とするため、同じベースブランチからスタック順序を推測しない。
6. **親子関係の変更者は 1 人、実装の書き込み担当者は並列にする。** 担当者は自分のブランチだけを push し、先端、現在のパッチベース、意図した親を報告する。親子関係を書き換えるのは親エージェントだけである。既存 PR を rebase、force-push、ベース変更する前に、親はその PR と全子孫へ「出荷」の手順 4 の予約解除と確認の規則を適用する。サービスが全要求の無効化を確認できなければ止まる。trunk は `<base-remote>` から fetch する。別のスタックブランチは `<head-url>` から直接 fetch する。`<head-remote>` は fetch URL がベースリポジトリ、push URL がフォークである可能性があるためである。選んだリポジトリの実体を使用中のサービスで検証し、fetch した対象を `<parent-tip>` として記録する。rebase 前に、`git ls-remote -- "$head_url" "refs/heads/$branch"` で子ブランチの公開 SHA を `<captured-sha>` として記録し、rebase 前のローカル先端との一致を必須とする。`git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` の成功も必須とする。親が変わったら `git rebase --onto "$parent_tip" "$current_base_sha" -- "$branch"` で子のコミットだけを移し、`<parent-tip>` を子の新しいパッチベースとして記録する。公開には `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"` を使う。head とベースが同じリポジトリなら、親ブランチをベースに子 PR を作成または変更する。解決したサービスと操作に応じて、`origin pr create --status open --base "$parent_branch"`、`gh pr create --base "$parent_branch" --repo "$base_repo"`、`origin pr edit "$pr" --base "$parent_branch"`、`gh pr edit "$pr" --base "$parent_branch" --repo "$base_repo"` を使う。head リポジトリがフォークなら、ローカルの子ブランチは親の正確な先端へ rebase した状態を保ちつつ、すべての PR はベースリポジトリの `<trunk>` を対象に作成または変更する。GitHub では承認済みのタイトルと本文を `<title>` と `<body>` に取得し、`gh api --method POST "repos/$base_repo/pulls" -f "title=$title" -f "body=$body" -f "head=$fork_owner:$branch" -f "head_repo=$head_name" -f "base=$trunk" --jq .html_url` で作る。「PR の作成」の準備状態の規則がドラフトを要求する場合だけ `-F draft=true` を追加する。それ以外では解決した Origin の対応操作を使う。ベース変更は `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"` または Origin の対応操作で行う。フォークにしかない親ブランチを、サービス上の PR ベースにはできない。`gt` でこの連鎖を送信、登録してはならない。
7. **親が差異を吸収し、変わったものを再検証する。** 親は `<base-remote>` から現在の trunk を fetch し、手順 6 の明示的な旧ベースと新しい親の指定を使って、連鎖を下から上へ rebase する。担当者のファイルに競合が出たら、その担当者が自分の範囲を直し、親が手順 6 の取得済み SHA を使う lease 付きの方法で結果を push する。rebase はそれより上のすべての SHA を書き換え、古い SHA の判定を無効にする。各 PR の判定 SHA における、記録済みパッチベースから head までの差分の安定版 `git patch-id` を、新しいパッチベースから head までの差分と比較する。パッチ ID が変わらなければコードの判定を維持する。変わったパッチは引き渡し前に手順 4 へ戻す。パッチ ID が同じでも、履歴を書き換えて push するたびにマージ可能性と CI を再確認する。追加承認の規則は Autopilot-full と同じである。新たな値の固定には、親による新しい追加承認のための停止が必要である。取り込み済みの値の差異を吸収することは引き上げではない。
8. **連鎖を引き渡す。** 成果物は、下から上の順序を固定した検証済み PR の一覧である。解決したサービスでレビューでき、各リンク先の PR 本文またはコメントに検証者の判定が付いていることを求める。同一リポジトリの head はベースブランチの連鎖を使う。フォークの head はローカルの親子関係を保ち、すべての PR は trunk を対象とする。操作者は現在の最下段 PR だけを、1 件ずつ「出荷」へ送る。準備完了時マージの要求は、「出荷」が全子孫の予約を解除して確認した後、その最下段だけに適用する。連鎖全体や子孫への準備完了時マージを提案、予約してはならない。

**2 つの自動実行方式の選び方。** PR が独立し、取り込み権限が与えられている場合は Autopilot-full を使う。操作者が取り込み前にレビューしたい場合、作業に順序や結びつきがある場合、またはマージ権限が与えられていない場合は Autopilot-stack を使う。

**返信に含める内容：** スタックの最下段と最上段へのリンク、各リンクの判定要約を 1 行ずつ、保留または対象外にしたものとその理由。
