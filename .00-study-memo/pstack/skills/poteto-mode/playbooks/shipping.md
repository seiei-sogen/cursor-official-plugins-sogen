### 出荷

**取り込む内容に責任を持つ。各 PR を独立に検証し、最下段から連続する検証済みの範囲だけを取り込む。その後はキューに手を加えない。**

これは `playbooks/babysit.md` に続く後半の手順である。

1. **ホスティングサービス、リポジトリの実体、2 つの Git リモートを解決する。** 既定は GitHub CLI の `gh` である。`command -v origin` が成功し、Origin がリポジトリを解決できれば、PR の表示、監視、編集に `origin pr ...` を使う。マージに使うのは、手順 5 の head 一致条件を利用できる場合だけである。それ以外は `gh` を使い、代替したことを記録する。サービスが報告したベースリポジトリを、正規の `<base-repo>` として記録する。GitHub では `<base-owner>` と `<base-name>` に分け、すべての `gh pr` コマンドに `--repo "$base_repo"` を渡し、GitHub 監視ツールにもその 2 要素を渡す。`<head-remote>` は、ブランチに設定された push リモート、`remote.pushDefault`、ブランチのリモート、曖昧さなく 1 つに決まるリモートの順に解決する。push URL が PR の head リポジトリを指すことを確認し、その正確な URL を `<head-url>` として記録する。取得したリモート状態と、条件付き push が同じリポジトリを扱うためである。`<base-remote>` は、fetch URL を `<base-repo>` と照合して独立に解決し、trunk に使う前に URL を確認する。push URL が head リポジトリ、fetch URL がベースリポジトリと一致すれば、同じリモート名が両方の役割を担ってよい。リモート名が 1 つのリポジトリを特定すると仮定せず、役割ごとに URL を比較する。解決した値やサービスが報告した値は、すべて直接シェル変数に取得する。コマンド例では `"$branch"`、`"$head_url"` のように、引用符付きの小文字変数を使う。値をシェルのソースへ貼り付けない。推測せず、サービス名を Git リモートとして扱わず、Graphite の `gt` を必須にしない。
2. **検証前にキューを固定し、マージ予約を解除する。** 下から上の PR 一覧を明示して固定する。同一リポジトリのスタックは、ベースブランチの連鎖と照合する。フォークの head では、すべての PR が trunk を対象にしておりサービス上のベースはスタックを表さないため、検証済みのローカルの親子関係から順序を取る。検証担当者を起動する前に、使用中のサービスで固定一覧のすべての PR を調べ、既存の準備完了時マージや自動マージの要求をすべて解除し、各要求が無効であることを確認する。GitHub では GraphQL で各 PR の `id`、`headRefOid`、`baseRefName`、`autoMergeRequest`、`mergeQueueEntry` を問い合わせる。`autoMergeRequest` が非 null なら `gh pr merge "$pr" --disable-auto --repo "$base_repo"` を実行する。`mergeQueueEntry` が非 null なら、`gh api graphql -F "id=$pr_node_id" -f query='mutation($id:ID!){dequeuePullRequest(input:{id:$id}){mergeQueueEntry{id}}}'` で `dequeuePullRequest` mutation を呼ぶ。この mutation に渡すのは PR のノード ID である。再度問い合わせ、`autoMergeRequest` と `mergeQueueEntry` の両方が null であることを必須とする。`autoMergeRequest` が null というだけでは、PR にマージ予約がない証明にならない。Origin では、そのサービスが示す取り消し操作を使い、別々に報告されるキューの状態をすべて確認する。一覧全体の予約解除を確認できなければ止まる。PR をまとめて担当させず、PR ごとに 1 人のサブエージェントを専用 worktree に置き、その PR の親と head の実際の操作面を比較する。最下段 PR のパッチベースは trunk である。各子のパッチベースは直前の PR の正確な head であり、サービス上では trunk を対象にするフォークの子も同じである。各サブエージェントは `PASS`、`PASS+NOTES`、`FAIL` を返し、自分の PR に判定を投稿する。安全とは、コードを書いていないエージェントから判定を得た状態である。CI の成功やボットの承認レビューは判定の代わりにならない。最下段から上へ進み、合格判定のない最初の PR で止まる。`PASS` と `PASS+NOTES` はどちらも合格である。その上限と、連続性を断つ理由を報告する。
3. **各判定が現在のパッチにも当てはまるか再確認する。** 合格判定の時点で `<verdict-sha>`、`<verdict-base-sha>`、`<verdict-base-sha>..<verdict-sha>` の安定版 `<verdict-patch-id>` を記録する。`<landing-sha>` と `<landing-base-sha>` は、その head とベースの値で初期化する。フォークの子のパッチベースをサービス上のベースに置き換えない。サービス上のベースは trunk なので、差分に未マージの親も含まれるためである。取り込み前に、使用中のサービスから現在公開されている head を `<current-head>` として読み、ローカルブランチの先端との一致を必須とする。`<landing-base-sha>..<current-head>` の安定版パッチ ID を計算し、`<verdict-patch-id>` と比べる。パッチが変わっていれば再検証する。変わっていなければコードの判定を維持し、`<landing-sha>` を `<current-head>` に設定して、その head でマージ可能性と CI を再実行する。パッチが等価な rebase により、`<landing-sha>` と `<verdict-sha>` が異なることはある。両方の値を保持する。コミットメッセージの一致や、古い SHA で成功したチェックを代わりに使ってはならない。
4. **最下段の PR だけを準備する。** ブランチやベースに触る前に、現在の最下段とすべての子孫を、使用中のサービスで調べる。GitHub では手順 2 の GraphQL 状態問い合わせを繰り返す。非 null の `autoMergeRequest` をそれぞれ無効化し、非 null の `mergeQueueEntry` をそれぞれキューから外し、すべての PR で両フィールドが null であることを確認する。Origin ではサービスが示す取り消し操作を使い、別々に報告されるキュー状態をすべて確認する。手順 2 の後に別の主体が予約を再設定した可能性に備え、この解除確認を繰り返す。対象のすべての PR を解除して確認できなければ、rebase、force-push、ベース変更、予約設定、マージのどれよりも前に止まる。`<base-remote>` から現在の trunk を fetch し、正確な先端を `<trunk-tip>` として記録する。検証済みの最下段ブランチを rebase する前に、`git ls-remote -- "$head_url" "refs/heads/$branch"` で公開 SHA を記録し、その `<captured-sha>` が rebase 前のローカル先端と一致することを必須とする。`git merge-base --is-ancestor "$landing_base_sha" "refs/heads/$branch"` の成功も必須とする。`<landing-base-sha>` と `<trunk-tip>` が異なる場合、`git rebase --onto "$trunk_tip" "$landing_base_sha" -- "$branch"` でこの PR のコミットだけを移し、`<landing-base-sha>` を `<trunk-tip>` にする。書き換えた履歴は `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"` で公開し、期待 SHA を指定しない lease や単純な force は使わない。その PR だけを `origin pr edit "$pr" --base "$trunk"` または `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"` で trunk 向けにする。ベース変更後は `baseRefName` を再取得し、`<trunk>` との一致を必須とする。`<trunk>` を `<landing-base-ref>` として記録し、コミットを表す `<landing-base-sha>` と分ける。push やベース変更の後は、手順 3 のパッチ比較と現在の head の確認を繰り返す。子孫のベース変更、予約設定、マージはまだ行わない。
5. **現在の取り込み SHA とベースを確認し、PR を 1 件ずつ取り込む。** マージや自動マージ要求の直前に、現在の `headRefOid` と `baseRefName` を読む。`headRefOid` は `<landing-sha>`、`baseRefName` は記録済みの `<landing-base-ref>` である `<trunk>` と一致しなければならない。この読み取りは事前確認であり、ロックではない。すべてのマージ操作には、サーバーが強制する head 一致の事前条件が必要である。GitHub では事前確認で一致した直後に、`gh pr merge "$pr" --squash --match-head-commit "$landing_sha" --repo "$base_repo"` を実行する。GitHub にサーバーが強制するベース一致条件はないため、防御機能を捏造したり GitHub の流れを無効にしたりせず、`baseRefName` を監視し続け、手順 8 でマージ先を確認する。Origin に文書化された head 一致オプションはない。使用中のサーバーがその防御を提供すると報告する場合だけ Origin でマージする。それ以外は、その機能があり解決可能なサービスへ切り替えるか、マージ前に止まる。必須条件がまだ実行中で、ユーザーが準備完了時のマージを求めている場合、独立した判定に対応する SHA 単位の必須検証チェックがリポジトリにあり、head 更新のたびに未充足へ戻る場合だけ、サーバー側自動マージを使う。GitHub では一致する事前確認の直後に `gh pr merge "$pr" --squash --auto --match-head-commit "$landing_sha" --repo "$base_repo"` を実行し、head やベースの変化を観測したら解除する。GitHub がマージせず必須のマージキューへ追加した場合、非 null の `mergeQueueEntry` を有効な予約として扱い、head とベースを両方監視し続ける。必須検証チェックがなければ、サーバー側自動マージを予約せず動的な監視を続け、準備が整った時点で条件付きの即時マージを実行する。その PR がマージされるまで次の PR の準備を始めない。
6. **GitHub の自動マージやマージキューの状態を、スタック全体の準備完了と解釈しない。** `autoMergeRequest` は 1 件の PR に GitHub 自動マージを要求したことを表す。`mergeQueueEntry` は 1 件の PR が GitHub 標準のマージキューへ入ったことを表す。一方が null でも、他方が非 null のことがある。どちらも、Origin の準備完了時マージが予約されたこと、子孫がキューに入ったこと、パッチ判定が最新であること、連続したスタックが安全であることの証明にはならない。現在の最下段 PR について両フィールドと使用中のサービスの状態を確認する。サービスが報告できなければ状態不明と述べる。
7. **マージのたびに計算し直す。** `<base-remote>` から trunk を fetch し、マージした SHA が含まれることを確認する。固定した下から上の一覧からマージ済み PR を外し、新しい最下段の head、`<landing-base-sha>`、チェック、パッチ ID を調べる。新しい最下段の `<landing-base-sha>` には、以前の親の正確な先端がまだ記録されている。手順 4 で旧親のコミットを外す前に、その値をサービス上のベースへ置き換えない。ホストが子のベースを自動変更することはあるが、そうなったと仮定しない。その PR 1 件について手順 3〜6 を繰り返す。独立した作業はこの連鎖に入れず、個別に出荷する。
8. **現在の最下段がマージまたは失敗するまで監視し、周囲のキューを変更しない。** Origin では `origin pr view "$pr" --checks --comments` と `origin pr checks "$pr" --watch` を使い、現在のバージョンの head SHA、ベースブランチ、自動マージ状態、マージキュー状態、PR を、マージ済みまたは阻止の報告まで読み直す。GitHub では、インストール済みプラグインの `skills/poteto-mode/scripts/watch-pr/watch-pr --owner "$base_owner" --repo "$base_name" --queued-stack --stack-prs "$bottom"` を、イベントによる再開のためだけに使う。再開のたびに `gh pr view "$pr" --json headRefOid,baseRefName,state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest --repo "$base_repo"` を問い合わせ、手順 2 の GraphQL 状態問い合わせで `mergeQueueEntry` を読む。チェック、キュー登録、マージを受け入れる前に、`headRefOid` が `<landing-sha>`、`baseRefName` が記録済みの `<landing-base-ref>` である `<trunk>` と一致することを必須とする。head またはベースが変わったら、非 null の `autoMergeRequest` を無効にし、非 null の `mergeQueueEntry` をキューから外し、現在の監視を止め、手順 4 を経て手順 3 に戻る。パッチが変われば再検証し、安定版パッチ ID が変わらなくても CI とマージ可能性を再確認する。確認したにもかかわらず別の head やベースへマージされたら、安全確認の失敗として報告し、スタックを続けない。`autoMergeRequest` と `mergeQueueEntry` が両方 null のまま PR がマージ可能になったら、手順 5 に戻ってマージする。`mergedAt` が非 null、または `state` が `MERGED` になるまで手順 7 へ進まない。`mergedAt` がないまま `state` が `CLOSED` になった場合、または必須チェックが終端の不合格結果になった場合は、自動マージやキュー登録が保留中でも失敗として停止する。診断前に、保留中の要求をすべて無効化またはキューから除去する。`UNSTABLE` だけでは失敗ではない。チェックが実行中なら監視を続け、完了したチェックは必須かどうかで判断する。`mergeStateStatus` が `DIRTY`、または `BEHIND` が取り込みを妨げる場合、保留中の要求をすべて無効化または除去し、手順 4 の条件付き rebase と手順 3 の再検証へ戻る。解消できない競合では止まる。チェックがまだ実行中、自動マージが有効、またはキュー登録がある間の `BLOCKED` は失敗ではない。ここでは「PR の見守り」のキュー向け停止条件 `WAITING` や `merge-queue` を使わない。dynamic モードの `/loop` で監視を維持する。マージのたびに結果と新たな上限を報告する。キューが停滞したら、変更する前に診断する。
9. **検証済みの上限で止まる。** 連続する検証済み範囲がマージされたら、取り込んだもの、次の未検証 PR、それを検証するために必要な作業を報告する。範囲を広げる場合は、手順 1 から新たに実行する。

**返信に含める内容：** 連続する検証済み範囲とその上限、各 PR の判定と判定者、有効にしたマージ予約とその確認方法、取り込んだもの、次の未検証箇所に必要な作業。
